02 推理运行时 · 专注 KV Cache 存储

推理过程动态图解：张量变化、连续批处理与 PagedAttention

推理运行时 · vLLM 请求源码 · 块管理器深入 · vLLM 与 SGLang 对比

推理里最难想象的三件事：一次前向中张量的形状怎么变、几十个请求怎样在每一轮动态拼成一个 batch、KV Cache 怎样被分页存放和读取。这一页用三个可以逐步播放的演示把它们画出来。点“下一步”或“自动播放”，也可以直接点说明跳到某一步；黄色框是这一步的重点。

读完应该能回答：为什么 Decode 受带宽限制？为什么连续批处理比静态批处理吞吐高？PagedAttention 到底省了什么、代价是什么？

1. 一次推理中张量怎样变化

模型参数取 Llama-3-8B 一类的公开配置，只为说明形状，不涉及具体实现细节。

对比Prefill（6 个 token）Decode（1 个 token）
输入张量[6, 4096][1, 4096]
注意力 scores[32, 6, 6]，因果掩码[32, 1, 7]，读全部历史 KV
每个权重被复用6 次（每个 token 一次）1 次
主要瓶颈算力显存带宽（读权重 + 读 KV）
KV Cache一次写入 6 个位置每步追加 1 个位置

所以提高 Decode 效率的核心是让更多请求一起算，把“读一遍权重”的成本分摊掉——这就引出了第 2 个演示。原理推导见 GPU 与 kernel 基础。

2. 连续批处理：每一轮怎样组 batch

演示的是 vLLM V1 一类“统一 token 预算”的调度思路：每轮先满足正在运行的请求，剩余预算再给新的 Prefill，长 Prefill 按预算切块。SGLang 的思路类似，但它还会参考前缀缓存决定谁先进（见对比页）。

方式怎么组 batch问题
静态批处理凑齐一组请求一起跑，等最长的那个结束才换下一组；序列要补齐到同样长度短请求早早结束后，GPU 空等；补齐浪费算力
连续批处理每轮重新选择参与的请求；结束的立刻离开，新的立刻加入；所有 token 拼成一维，不补齐需要分页的 KV 管理和能处理不等长序列的注意力 kernel
+ chunked prefill长 Prefill 按预算切块，和 Decode 混在一轮里Prefill 被拆成多轮，单个请求的 TTFT 可能变长；预算需要调

3. PagedAttention：块表与物理块

代价也要知道：注意力 kernel 要按块表收集不连续的数据，比读连续内存复杂；块太小会让块表变长、kernel 效率下降，块太大又会增加尾部浪费并降低前缀命中精度。vLLM 默认块大小是 16 个 token。
