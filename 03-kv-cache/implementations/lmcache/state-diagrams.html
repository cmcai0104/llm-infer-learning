对应阅读：推理语义见 公共基础；运行时见 LMCache 内核；存储见 存储与 Mooncake； 生产问题见 性能与运维。

MP 架构：谁决定、谁执行、谁存储

常见配置中 L1 是主机 DRAM，L2 是外部后端。当前实现还支持其他 L1 backing， 因此 L1/L2 是 LMCache 的管理层级，不是 CPU 硬件 cache 层级。 MP 也有 engine-driven transfer，图中的跨进程传输并不限定由 server 发起。

进程内模式对照

这条路径适合理解旧教程。它与 MP 共享一些底层能力，但 ObjectKey、L2 adapter 和 MP server 参数不能直接套用到进程内配置。

冷请求：计算后存储

这是依赖关系图，并不表示每次 STORE 都同步阻塞 scheduler。 只允许存储引擎声明已完成的有效 token 范围；尾部不完整 chunk 和 decode 写回时机由具体路径及策略决定。

热请求：L1/L2 查找、预取、回填 GPU

关键区别是 lookup ack、预取完成、GPU 可读 三个时刻。多 server 的命中聚合 在本基线采用共同可用前缀，不能取“最快 server 的最长结果”。

L1 对象状态与生命周期

图中 staging 是 writer 的私有对象，resident 是同 key 的公共对象； “Discarded→Absent”只描述被丢弃的 staging 生命周期。多个 writer tag 可以同时拥有同 key 的 staging；不应把这幅简图理解为整个 key 的单一互斥状态机。 锁过期也不等于 GPU/DMA 自动停止，设备操作的完成与内存回收必须另行协调。

LMCache 与 Mooncake 组合

Master 管对象位置与生命周期；Transfer Engine metadata 管 segment、 buffer 和 endpoint 信息，两者不是同一层元数据。 本图展示常见的主机 L1 路径，不承诺该 adapter 自动执行 GPU 到远端 GPU 的 GPUDirect RDMA，也不把控制 RPC 画成大对象传输路径。

P/D 分离与跨请求复用

P/D 分离解决阶段独立扩缩与干扰；跨请求缓存解决重复 prefill。 当前仓库的 MP P/D recipe 使用 MultiConnector 组合 NIXL 与 LMCache， 并要求两个引擎各自配套 server；它不是“把 Mooncake Store 开关打开就自动完成 P/D”。
