05 数据传输 · 专注 KV Cache 存储

远端 KV 的搬运与就绪：什么时候值得搬，什么时候才能用

一个请求命中了共享前缀，而这段前缀的 KV Cache 不在本机 GPU 上，只在远端的对象存储里。这时要回答两个不同的问题：值不值得搬——把字节搬过来的总代价是否低于在本地重新算一遍；以及什么时候才算能用——哪一个信号真正允许 GPU 上的注意力计算读这块显存。这两个问题常被合在一起讨论，于是出现“带宽明明够、首 token 时延却没降”的现象。首 token 时延（Time To First Token，TTFT）指从请求到达到生成第一个输出 token 的时间，下文统一用 TTFT 指代。

本页沿着同一条数据流走一遍：远端对象 → 主机内存 → GPU 块，依次算字节、算对象数、算时间，再解释真实系统为什么偏离这些下界。具体某个框架的回收契约、返回码与源码位置不在这里重复，需要时看联合链路页的回收交接设计；远程直接内存访问（RDMA）侧的切片、选路与完成状态见Mooncake Transfer Engine 实现案例。本页所有时间数字都是按明确给定的前提做的算术推导，没有 GPU 或网络实测；引用的论文与社区报告属于特定系统、特定版本上的研究与观测。

1. 先把资源和时刻命名

1.1 三个资源：S、H、B

一次远端恢复至少涉及三处内存，它们的持有者、单位和可复用条件都不同。为了后面能逐段记账，先固定名字：

  • S（Store object）：远端对象存储里的一个对象，由 key 标识。一个对象里可能装了很多 token、很多层。副本数、是否有带时限的读保护（租约）、失败后能否部分发布，都由具体存储协议决定，不是对象的天然属性；下文凡用到这类保护，都会写清是哪种协议前提。
  • H（host staging / resident）：本机主机内存里的暂存或已发布副本，既是网络传输的落点，也是后面设备拷贝的源。只有当网卡要直接读写 H 这个地址时，H 才必须是向网卡注册过（建立了地址映射与访问权限）的内存区；如果字节先落进另一块已注册缓冲、再由 CPU 复制到 H，那么 H 本身不必是注册区，但多出一次复制。
  • B（GPU blocks）：引擎为这个请求分配的目的 GPU 块集合，单位是“块”（页），块大小由引擎配置决定。注意力计算最终读的是 B。

三者的释放条件要分开判断：某次等待超时只表示这次等待结束了，不表示底层操作已停止。H 要等仍可能读写它的传输与设备拷贝都结束，并解除后续使用者的持有，才能复用；B 同样要等所有可能访问它的设备操作结束，并解除所有使用者的持有。若 B 被多个请求共享，只结束当前请求还不够。S 的空间由存储侧按协议确认相关访问已结束或无法继续访问后回收。具体如何确认、超时后由谁继续持有资源，须按相应实现的契约核对。

1.2 五个时刻：定位、提交、搬运、设备就绪、调度使用

正常路径按这个顺序走，每一步的“完成”含义都不一样：

  • 对象定位：按 key 查询哪些对象存在、在哪里。查询返回只说明目录被查过，字节还没动。
  • 提交：把“从哪个远端地址读、读多长、落到哪个本地地址”交给传输层。提交函数返回成功，只表示任务被接受。
  • 字节搬运完成：传输层报告这次操作的字节移动结束，覆盖范围仅限这次操作声明的地址。
  • 对象可读 / host 发布：上层确认所有必要片段都齐了，把 H 从暂存状态发布为可读。缺一个片段，前面所有“搬运完成”都不能让这段前缀可用。
  • 设备就绪与调度使用：H 到 B 的拷贝在某个设备流上执行，完成由设备事件表达；而“B 里有正确数据”与“这个请求现在就有 GPU 执行机会”仍是两件事——能否进入本轮批次，由调度器的队列顺序、批大小、token 预算和分块预填充决定。

这条链路上最常见的错误推理，是用前一个时刻的信号替代后一个时刻的证据。第 7 节会给出一组分段时延，说明代价可能几乎全部落在“字节已经到了主机内存之后”。

1.3 恢复路径与 PD 搬运不是同一笔账

两种常见的跨机 KV 流动，字节账不同。恢复（S→H→B）：对象早已在远端，本机只需读入再送上 GPU，计两段——网络段与 H2D 段（host to device，主机内存到设备内存）。预填充与解码分离（PD disaggregation）里的新 KV 搬运：KV 刚在源侧 GPU 上算出来，要送到另一台机器；若走主机内存中转，源侧还要先做一次 D2H（device to host，设备内存到主机内存），于是是三段。段数多一段，第 4.3 节会看到它在流水模型里的代价也更大。

还要分清两种常被混为一谈的“直连”。RDMA 指在已授权的内存区上直接做数据访问，减少远端 CPU 参与数据复制；它不自动等于网卡直接读写 GPU 显存。后者需要 GPUDirect RDMA 这类能力，依赖硬件、驱动、总线拓扑与设备侧可见性条件。同样，“零拷贝”必须说清省掉了哪一次复制：语言运行时对象层的复制、应用缓冲与传输暂存缓冲之间的复制、网络栈与远端 CPU 的复制、主机与设备之间的搬运及布局转换，是四个不同层次，省掉一层不代表另外三层消失。只要路径仍经主机内存中转，H2D 的字节就必须照算。

2. 同一份字节，三种“块”

2.1 基准场景 S0

全页用同一个场景，便于交叉验算。S0：同构全注意力模型，80 层，8 个 KV 头，head_dim = 128，BF16（每元素 2 B），前缀长度 32,768 token；部署为张量并行 8 路（tensor parallel，简称 TP8，即把同一层的权重与 KV 头切到 8 个进程上，每个进程称一个 rank），按 KV 头均匀切分；假设无副本、无填充、不计元数据。

每个 token 的 KV 字节数（K 与 V 各一份，所有层合计）：

2×80×8×128×2 B=327680 B/token

整段前缀：

327680 B/token×32768 token=10737418240 B=10 GiB

在上述前提下每个 rank 承担 10 GiB÷8=1.25 GiB，即 1,342,177,280 B。这是给定前缀长度下的确定容量，不是用平均序列长度估的期望值；做容量上界要用允许的最大前缀。

3. 对象粒度：字节没变，控制面的工作量变了

3.1 两种布局的对象数

布局甲每 rank 128 个 10 MiB 对象，TP8 共 1,024 个；布局乙每 rank 10,240 个 128 KiB 对象，共 81,920 个。两者总字节完全相同，对象数差 80 倍。注意两种布局的 token 粒度是同一个值 256：布局乙切的是层，不是 token，所以它并不改变前缀能对齐到的 token 边界。

3.2 把对象数换成对象率

控制面（元数据查询、key 解析、任务登记、完成汇总）的工作量按对象计，不按字节计。设整个 TP8 组的元数据请求统一交给一个串行 worker，每个对象固定 20 μs，则它的服务能力上限是

120 μs/对象=50000 对象/s

假设系统每秒确实要从远端恢复 10 次 S0 量级的数据，两种布局的对象率是：布局甲 10×1024=10240 对象/s，约为上限的 20.5%；布局乙 10×81920=819200 对象/s，是上限的 16.4 倍。换个角度看单次恢复的控制面串行下限：布局甲 1024×20 μs=20.48 ms，布局乙 81920×20 μs=1638.4 ms。第 4 节会看到同样这份数据的网络下界是百毫秒量级，所以在这组假设下布局乙先打满控制面，字节通道还没用满。

批处理能摊薄每次远程调用的往返与系统调用开销：把 160 个对象打成一个批，调用次数降到 1/160。但它不消除每个对象自身的处理——key 解析、目录查找、地址登记、逐对象结果汇总仍按对象计。批处理改变的是“每批固定开销 ÷ 批内对象数”这一项，不是上面那 20 μs。这个 20 μs 本身是教学设定值，真实系统要实测，而且可能随并发升高而变化。

3.3 粒度有四种，不要互相替代

讨论“块太小”“对象太大”之前，先把四种粒度分开，它们可以独立选择：

  • token 粒度：一个对象覆盖多少连续 token。它决定前缀能对齐到的边界，因此决定部分命中时可复用的最小范围。布局甲乙都取 256，按层拆不改善 token 对齐。
  • 层粒度：一个对象覆盖多少层。它决定“能不能只拿到前几层就开始干活”。要把这件事变成真实收益，还需要引擎支持部分就绪与部分消费——即允许某些层的 KV 先到就先执行那几层；若引擎必须等全部层齐备，按层拆开只增加对象数，不产生流水价值。
  • 发布粒度：存储协议以什么单位把数据从“写入中”变成“可读”。是否允许一个对象部分发布、失败后是否必须整对象重写，由协议决定，不能从对象大小推出。
  • 传输重试粒度：传输层以什么单位重发。网络层面的丢包通常由传输协议自己重传，并不等于一个 Store 对象失败；只有当协议把这次操作判为失败并向上报告时，才涉及对象级的处理。

所以粒度是一个权衡，而不是“越大越好”或“越小越好”：用对象率对比控制面上限，用字节量对比链路上限，再分别核对发布与重试语义，然后才能选，并且写明选的是哪一层的粒度。

4. 带宽与拓扑：下界、速率口径、流水

4.1 线速下界，以及两种互斥的拓扑假设

先把链路速率换成字节速率。400 Gbit/s 裸线速（分母里的 8 是 8 bit/B，230 是 230 B/GiB）：

400×109 bit/s8 bit/B×230 B/GiB≈46.566 GiB/s

拓扑甲：整份 10 GiB 走一条共享的 400 Gbit/s 链路。

10 GiB46.566 GiB/s×1000 ms/s≈214.748 ms

拓扑乙：每个 rank 有一条独立且无争用的 400 Gbit/s 网络路径，每 rank 搬 1.25 GiB：

1.25 GiB46.566 GiB/s×1000 ms/s≈26.844 ms

甲与乙是互斥假设，214.748 ms 与 26.844 ms 不能放进同一张预算表。两者都是理论下界，还没算协议开销、排队、内存访问和同步。写预算时先画拓扑，再决定用哪一行。

4.2 两个速率口径，和有向的资源预算

“有效带宽”这个词同时被用在两个不同口径上，混用就会把同一笔开销算两次。本页区分：

  • 稳态字节服务率 v：某一段在真正搬运字节时的持续速率，单位 GiB/s。它不含控制动作的时间。
  • 全程有效吞吐：搬完 D 字节的总耗时 T 折算出的 D/T。它已经把控制开销包含在内，所以不能再叠加一次固定开销。

只有在“控制开销与字节搬运完全不重叠”这个教学假设下，才能写成两项相加：

T=nα+Dv,全程有效吞吐=DT

其中 n 是操作次数、α 是每次操作不随字节增长的那部分开销。真实系统里这两者常有部分重叠，重叠多少要实测；本页不假定某个重叠比例。这个模型解释了小对象为什么“带宽看着没打满”：字节项很小，时间几乎全在 nα 上，而这时 D/T 很低并不说明链路慢。

更要紧的是谁和谁共享同一份容量。记账要带方向，因为高速串行总线一般是全双工的——两个方向各有自己的容量。这条恢复路径上的有向需求是：

资源方向本路径上的需求
网卡所在链路网络 → 主机内存（入站写）网络段的全部字节
主机内存子系统写入 + 读出同一份字节先被写进 H，再被读出去做 H2D，即两次访问
GPU 所在链路主机 → 设备H2D 段的全部字节
GPU 所在链路设备 → 主机本恢复路径不用；PD 搬运的 D2H 走这个方向

规则是：按资源实际共享的容量合并需求。全双工链路的两个方向分别记账，同一方向的需求才相加；若资源提供的是读写合计能力，例如某个内存控制器，则读写需求要一起核对。网卡的入站写与 GPU 的主机到设备传输可能占用相反方向，仅凭“挂在同一个交换节点下面”不能把两者加到一个单向容量上。主机内存那两次访问会形成压力，但折算成具体的 DRAM 流量还受缓存与平台实现影响。

一个可以算的自检：若在 TP8 里为每个 rank 都假设 25 GiB/s 的 H2D，聚合需求是 8×25=200 GiB/s，折合 214.748 GB/s（十进制）。Mooncake 论文在分析某一特定模型与机型时，把主机到设备带宽这一参数取为 128 GB/s。两个数字摆在一起，说明“每 rank 各自独立的 25 GiB/s”这个假设必须对着真实平台的链路数、拓扑与内存能力核一遍；论文里的分析参数既不是普适上限，本页也没有在任何机器上实测过。

4.3 max 是理想界：一个说清前提的流水模型

“网络和 H2D 可以重叠，所以总时间取两段的 max”这句话需要一组前提。本页用下面这个教学模型，五条假设都写出来：① 数据被切成 n 个等大流水块；② 每段的服务时间与字节数成线性，所以分块后每块在第 i 段耗时 ti/n；③ 缓冲充足，上游不会因下游没取走而停顿；④ 各段之间没有共享资源争用（按 4.2 的有向预算核过）；⑤ 数据依赖允许按块发布与消费，下游拿到一块就能处理这一块。

记各段时间之和为 S，最慢一段为 tmax（若有多段并列最慢，指定其中任一段为瓶颈段即可）。第一块要依次穿过全部段，用 S/n；此后每隔 tmax/n 出来一块，还剩 n−1 块：

T0(n)=Sn+(n−1)tmaxn=tmax+S−tmaxn

第二项就是填充与排空的代价：n=1 时它等于其余各段之和，即退回串行；n 很大时它趋于 0，T0 才趋于 tmax。段数越多（例如 PD 路径的三段），分子 S−tmax 越大，同样块数下离 max 越远。

如果再加一条假设——每块引入固定开销 α、整段另有一次性开销 c0，且这两者都完全不能与字节搬运重叠——才能写成相加形式：

T(n)=tmax+S−tmaxn+c0+nα

这里的 n 只能取可行的正整数。它也不是 Store 对象数，也不是传输切片数：一个流水块可以聚合多个对象，把搬运切得更细也不自动改变 key 的数量。把这三件事当成一个变量，是粒度讨论里最容易出的错。

5. 一个能复算的选择例：搬还是重算

5.1 单 rank 的两段账

把问题缩到一个可以隔离测量的对象上：S0 的一个 rank，payload 1.25 GiB。教学设定：网络稳态字节服务率 20 GiB/s，H2D 25 GiB/s，不可重叠的一次性开销 3 ms（目录查询、提交、事件同步等），到同一终点的全量重算 70 ms。都是假设值。

tnet=1.25 GiB20 GiB/s×1000 ms/s=62.5 ms,th2d=1.25 GiB25 GiB/s×1000 ms/s=50 ms

整段下载完再整段上卡，即 n=1：62.5+50+3=115.5 ms。块数足够多、忽略每块开销的理想流水：62.5+3=65.5 ms。

和 70 ms 重算相比：串行 115.5 ms 亏，理想流水 65.5 ms 赚。同一条链路、同一份字节，仅因为“是否真的重叠、分得够不够细”就跨过了盈亏线。所以比较时必须声明：三者终点相同，都终止于“B 可被注意力计算消费”，不是“H 已就绪”，也不是“提交函数已返回”；重叠是前提而不是默认能力。

顺手核一下这组假设的自洽性：每 rank 20 GiB/s 折合约 171.8 Gbit/s 的有效速率，需要有一条能稳定提供这个速率的独立网络路径；在 400 Gbit/s 的链路上这意味着约 43% 的线速利用率。这只是说假设没有越过线速，不是可达性的证明。

5.2 要多细才真的赚

代入 4.3 的模型（两段，瓶颈是网络，S−tmax=50 ms，先取 α=0）：

T(n)=62.5 ms+50 msn+3 ms

要不劣于 70 ms 重算，需要 50/n≤4.5，即 n≥12（n=12 给 69.67 ms，n=11 给 70.05 ms）。只切成 8 块时 T=71.75 ms，仍然亏——“做了流水”和“流水已经足够细”是两件事。

把每块开销加回来，在 α>0 时，50 msn+nα 在正实数范围内的最小值出现在 n∗=50 msα，最小值为 250 ms×α。n∗ 只是一个连续放松的候选值；实际要检查其相邻的可行整数和边界，若系统还限定了最大块数或对齐粒度，也要计入约束。两个算例：

  • α=0.05 ms：候选 n∗≈31.6，取 n=32 得 50/32+1.6=3.16 ms，总计约 68.7 ms，仍优于重算。
  • α=0.2 ms：候选 n∗≈15.8，取 16 得 3.125+3.2=6.33 ms，总计约 71.8 ms，无论怎么调块数都赢不了重算。这是“足够大的每块开销会抹掉流水收益”的一个充分示例，不是临界值。

在这个加法模型里临界条件可以直接解出来：可行要求 250 ms×α≤4.5 ms，即

α≤(4.5 ms)24×50 ms=0.10125 ms

这是连续放松下的必要条件；由于 n 必须取整数，恰好等于 0.10125 ms 时最近的整数（22 或 23）给出的值已经略超过 4.5 ms，所以整数约束下可接受的 α 还要再小一点。这条结论只对“α 完全不可重叠且与块数成正比”的这个模型成立；换模型就要重新推。

5.3 推广到 TP 组，以及这个数字不是什么

上面算的是一个 rank。TP 组要一起才能开始计算，所以组时间是

Tgroup=maxrTr+tsync

用 8 个 rank 的平均值代替最慢的那个，会系统性低估：只要有一个 rank 的路径被别的流量挤到 12 GiB/s，它的网络段就是 104.2 ms，整组的理想流水也退到 107.2 ms 以上，远过 70 ms 的盈亏线。tsync 指各 rank 对齐到同一起跑点所需的时间，它具体由哪种同步原语实现、开销多大，取决于框架，本页不预设。恢复还要求各 rank 对同一段连续前缀都成功；某个 rank 少拿一个 chunk，可跳过的范围就按最小的那个折叠。

三件事这些数字不是：不是完整的 TTFT——队列等待、剩余 token 的计算、布局转换、采样都在外面；不表示任何框架已经实现了理想分块流水；不能用命中率替代——命中率告诉你“有多少可以不算”，不告诉你“搬过来是否比算更快”。

6. 传输态压缩：省的是哪一段字节

6.1 机制：不保留张量形状，编成比特流

CacheGen 处理的正是“把 KV 从别的机器取过来太慢”这个问题，思路是不保留运行时的张量形状，把 KV 编成更紧凑的比特流。按论文自述，它由三步编码加一层流式自适应组成：

  • 锚点与差值编码：把上下文按若干连续 token 分组，组内第一个 token（锚点）独立压缩，其余 token 只记录相对锚点的差值。依据是论文观察到的 token 维局部性——同层同通道内邻近 token 的 K/V 取值更接近，差值的分布比原值更集中。选同一个锚点而不是逐对相邻差分，是为了让组内编解码可以并行。
  • 按层差异化量化：论文观察到浅层的精度损失对输出质量影响更大，于是按层分组、越深的层用更粗的量化；锚点 token 保持较高精度，因为它影响整组差值的分布。
  • 熵编码：对量化后的符号做无损编码，并按通道与层的组合分别统计概率分布，再用这些分布去编码。分布从哪些数据统计、复用范围多大，属于实现选择，本页不下“对所有 KV 都复用同一套固定分布”这类强断言。
  • 按块自适应：上下文切成块，每块可编成多个压缩等级、可独立解码；运行时按实测吞吐为下一块选“能满足时延目标、损失最小”的等级，带宽太低时回退到直接传文本、让 GPU 重算这一块。

解码侧在他们的实现里放在 GPU 上，并与下一块的传输重叠。这里有两条边界值得记住。第一，这类方法减小的是传输态字节：解码之后要被注意力计算读的仍然是运行时需要的数据类型与布局，恢复到相同运行态时 B 的占用不会变小。想减小运行态占用是另一类技术，既包括丢 token、改注意力结构，也包括直接对运行态 KV 做量化（代价是改变了运行态表示，和这里的“同运行态恢复”不是同一个比较）。第二，压缩是有损的，论文在其模型与数据集上报告了质量退化很小，但这属于那套配置下的结果；换模型、换任务都要重新验证，本页不给任何未实测的质量承诺。

6.2 同起点、同终点的成本账

比较必须从同一个决策时刻出发：此刻缓存路线手上已经有 S 里对应的对象，重算路线手上已经有 token。两条路线共同的前置阶段（请求到达、分词、调度决策本身）都不计入任何一方。另外，对照组也要配套：和“压缩对象”比较的那条未压缩路线，前提是 S 里存在对应的未压缩对象。

沿用 5.1 的单 rank 参数，设线上压缩比 4，即网络字节从 1.25 GiB 降到 0.3125 GiB。3 ms 的一次性开销按“三条搬运路线共用”处理；重算那一侧的 70 ms 已按同终点口径给出，不再叠加这 3 ms。若编码不是离线完成而是在保存路径上在线做，那笔时间要记在生产侧，不出现在下表。

两个解码成本采用如下口径：d 是在 GPU 上解码、并在 B 中产出可被注意力计算消费的完整张量（含所需布局）所花的时间；c 是在 CPU 上解码、并在 H 中产出完整张量（含 H2D 所需布局）所花的时间。表中未压缩路线也假设布局已兼容；若还要转换，须另计到同一终点的成本。

6.3 “压缩了，仍然不如重算”的完整反例

前提全部给定：单 rank payload 1.25 GiB；压缩比 4；网络 20 GiB/s；H2D 25 GiB/s；搬运路线共用的一次性开销 3 ms；同终点重算 70 ms；解码在 CPU 上，解码吞吐按输出字节计为 2 GiB/s（教学设定值），即产出完整的 1.25 GiB 需要 625 ms。则

T=15.625+1.25 GiB2 GiB/s×1000 ms/s+50+3=693.625 ms

网络字节确实省掉了四分之三（62.5 ms 降到 15.625 ms），但解码把 625 ms 加了回来；而且因为在 CPU 上还原成完整张量，H2D 的 50 ms 一分没省。要让这条路线不劣于重算，CPU 解码必须快到 1.375 ms 以内。结论的形式很重要：压缩降低的是线上字节，盈亏要看解码放在哪里、H2D 还剩多少字节、以及质量是否仍在可接受范围内。

7. 观测：把时间切开，再归因

7.1 至少要分开的六个区间

一条恢复路径上，下面六段必须分别打点，否则无法区分“带宽不够”和“已经到了却没被用上”：

区间测的是什么变大时优先怀疑
lookup / 目录查询按 key 问“有没有、在哪里”的往返元数据服务排队、对象数过多、调用未批量
IO 排队任务提交后到真正开始搬的等待并发准入、队列深度、容量被其他流量占住
IO 搬运字节真正在链路上移动的时间字节量、稳态服务率、同资源同方向的争用
IO 完成 → host 发布片段齐了之后把 H 标记为可读、登记索引发布动作被挂在哪个线程、哪个检查点上
发布 → H2D 完成设备拷贝的提交与完成H2D 服务率、流与事件依赖、与计算争用
H2D 完成 → 被调度执行这个请求真正进入某一轮批次队列顺序、批大小、token 预算、分块预填充

7.2 “IO 完成”不等于“可以跑了”

第 4 段之所以单列，是因为它可以大到压倒前面所有段。SGLang 社区的一份 issue 报告了一个结构性原因：当分层缓存接了后端存储时，一个等待中请求的预取只有在调度器按先到先服务顺序扫到它时才被最终确认（插入主机侧索引、释放占用、清理在途记录）。于是“确认预取已完成”这个动作被绑在了请求在等待队列中的位置上——队列很深、当前几轮的 token 预算被队首吃光时，扫描根本到不了后面的请求。

报告者给出的自测数据里，这个落差很明显：一次部署中存储 IO 本身约 91 ms，而调度器侧的确认滞后约 2.4 s；另一次运行的分位统计中，“IO 完成到确认就绪”这一段的 p50 为 261 ms、p99 为 22.16 s，而同一次运行里真正的存储 IO 这一段 p50 只有 26.7 ms。他们提出的修法是把确认从队列位置上解绑：在调度器已有的检查点主动扫描在途预取，对本地已就绪的操作直接调用原有的进度检查，并在并行组之间约定一致的处理集合与顺序。

两处边界要一起记住。第一，这是报告者在其部署上的观测，本页没有复现，也没有证据表明相应修改已被合并。第二，更通用的一点：他们自己写明，这个改动只把确认时刻提前，不改变准入语义——能否进入预填充批次仍由等待队列顺序、批大小、token 预算和分块预填充决定。社区把确认后的状态叫作 “ready”，这是“预取结果已确认、该请求可以被考虑”的意思，不是“GPU 开始算了”。

由此还能推出一条容易被跳过的因果关系：准入规则不变，并不意味着各段时长不变。假设确认提前了 Δ，后面的设备拷贝也相应提前完成，但这个请求真正入批的时刻仍被 token 预算卡在原处——那么“H2D 完成 → 被调度”这一段就会增加 Δ，总完成时间一点没变，只是等待从一段挪到了另一段。反过来，如果这个请求原先正是因为“还没确认”而错过了某一轮批次，那么提前确认能带来多少改善，取决于后续有没有合适的准入机会，也取决于其他请求的负载反馈——它们的排队状态也会因为这次改动而变化。所以不能用“规则没改”推出“区间不变”，也不能拿单一指标的变化去认定某一个原因。

7.3 一次能说明问题的实验怎么设计

要让分段数字支持结论，变量必须一次只动一个，其余固定：相同的到达过程、相同的队列与准入策略、相同的请求长度分布、相同的命中率、相同的时延目标。然后分别检验三类因素，并且把竞争解释一起列出来：

  • 字节：改压缩比或改 payload，看 IO 搬运段怎样随字节变化。字节翻倍而该段几乎不变，与“该段以固定开销为主”一致，但也与“存在排队或争用把时间摊平”一致；要排除后者，需要同时记录并发度、同方向上的其他流量，以及单次操作的字节数与完成时刻。单看“时间没变”不足以排除链路因素。
  • 对象率：固定总字节，只换对象粒度（如第 3 节的两种布局），看 lookup 段与 IO 排队段的变化。这是检验控制面能力的直接手段，前提是不要同时改了批量方式。
  • 确认与准入：固定前两者，只改“IO 完成 → 发布 → 被调度”的确认路径，并按 7.2 的分析把各个时间戳分别记下来。若报告时间变好而 TTFT 不变，要先看等待是否只是挪到了后一段。

报告时把传输 microbenchmark、对象读写吞吐和最终推理指标分开，并注明每个数字是否包含注册、建连、主机暂存和设备同步。还有一个容易被当成结论的平均量：“单请求字节 × 到达率”给出的是平均容量需求，它是一个必要预算（配不够就一定堆积），但不足以保证时延可忽略——突发、排队和尾部分布都在这个乘积之外。DistServe 论文就是用这个乘积来说明分离式部署的带宽预算，同时用排队模型分析时延，并且指出在不同放置方式下传输占比的结论会完全不同。

没有 GPU 或高速网络环境时，仍然能做两件有价值的事：按本页方法复算字节与时间预算，以及在给定到达过程与准入策略下模拟排队。复算和模拟都不是实测，报告时要照此标注。

题 1

(a) 每 token 仍是 2×80×8×128×2 B=327680 B。总字节：

327680 B/token×8192 token=2684354560 B=2.5 GiB

单 rank：

2.5 GiB÷8=0.3125 GiB=320 MiB=335544320 B

GPU 块：8192÷16=512 块/rank，每块 655,360 B = 640 KiB，核验 512×655360=335544320 B。

chunk 数 8192÷256=32。布局甲：每 rank 32 个 10 MiB 对象，TP8 合计 256 个。布局乙：每 rank 32×80=2560 个 128 KiB 对象，TP8 合计 20,480 个。核验总字节：256×10485760=2684354560 B，20480×131072=2684354560 B，两者与 GPU 块侧完全一致。对象数差 80 倍，字节数一字不差——这是粒度讨论的起点。

(b) 单 worker 能力 1÷20 μs=50000 对象/s。布局甲 20×256=5120 对象/s，约为能力的 10.24%；布局乙 20×20480=409600 对象/s，是能力的 8.192 倍，单 worker 无法承受。

所需 worker 数 ⌈8.192⌉=9。九个 worker 的合计能力是 450,000 对象/s，利用率为

4096009×50000≈91.0222%

剩余能力 450000−409600=40400 对象/s。这个“9”能支持的结论只有一条：在理想均分下，容量不低于需求的最小整数个 worker 是 9。它依赖三个必须写出来的假设——负载完全均分、worker 之间没有额外的协调或共享结构开销、每对象 20 μs 不随并发变化。它不能支持任何时延结论：排队时延还取决于到达过程与服务时间的分布，本题没有给这些信息，所以 9 既不是容量规划建议，也不是任何服务目标的保证。

(c) 控制面串行下限：布局甲 256×20 μs=5.12 ms；布局乙 20480×20 μs=409.6 ms。

网络下界的分母是 400×109 bit/s÷8 bit/B=5×1010 B/s。共享单链路：

2684354560 B5×1010 B/s×1000 ms/s≈53.687 ms

每 rank 独立路径：

335544320 B5×1010 B/s×1000 ms/s≈6.711 ms

两个拓扑互斥，不能混用。比较：布局乙的控制面下限 409.6 ms 既远大于 53.687 ms 也远大于 6.711 ms，所以在这组假设下它先在控制面触顶，字节通道没被用满；布局甲的 5.12 ms 小于两个网络下界，控制面不是瓶颈。

但这不足以断言布局甲总更好，按四种粒度分别看：

  • token 粒度：两种布局都是 256，所以前缀能对齐到的边界、部分命中时可复用的最小范围完全相同。按层拆不带来任何对齐上的好处，这是最容易被想错的一条。
  • 层粒度：布局乙让“先拿到前几层就先干活”在存储侧成为可能，但要变成真实收益，必须引擎支持部分就绪与部分消费；若引擎要求全部层齐备，按层拆只增加对象数。
  • 发布粒度：一个对象能否部分发布、失败后是否必须整对象重写，由存储协议决定，不能从 10 MiB 还是 128 KiB 推出来。
  • 重试粒度：网络层的丢包一般由传输协议自己重传，不等于一个 Store 对象失败；只有协议把这次操作判为失败并上报，才涉及对象级处理。所以“小对象重传更便宜”不是自动成立的论证。

另外，20 μs/对象与单 worker 都是教学设定；换批量接口或多 worker 之后对象率上限会变。正确的说法是“在给定的对象率需求与这套控制面假设下，按层拆到 128 KiB 会先打满控制面”。

题 2

(a) payload 0.3125 GiB：

tnet=0.3125 GiB20 GiB/s×1000 ms/s=15.625 ms,th2d=0.3125 GiB25 GiB/s×1000 ms/s=12.5 ms

n=1：15.625+12.5+3=31.125 ms；块数足够多且忽略每块开销：15.625+3=18.625 ms。相对 18 ms 重算：串行亏 13.125 ms，理想流水也亏 0.625 ms。这是本题的关键——连理想界都过不了线，就不必再争“实现有没有做好流水”。终点定义：三者都终止于“B 可被注意力计算消费”，即本次若确有设备工作，相应的设备完成事件已完成且结果为成功；不是“H 已就绪”，也不是“提交已返回”。

(b) 要 max(tnet,12.5)+3≤18。H2D 分支给 15.5 ms，已满足；约束落在网络段：tnet≤15 ms，于是

Bnet≥0.3125 GiB15 ms×1000 ms/s≈20.8333 GiB/s

换算为位速率：

20.8333 GiB/s×230 B/GiB×8 bit/B109 bit/Gbit≈178.96 Gbit/s

在一条 400 Gbit/s 链路上，这要求约 44.7% 的线速利用率——一个需要实测确认的目标，不是自动达到的。

(c) 网络也是 25 GiB/s 时两段各 12.5 ms，S=25 ms。两段相等时指定任一段为瓶颈段即可，S−tmax=12.5 ms，结果与选哪一段无关：

T(n)=12.5+12.5n+3≤18⇒12.5n≤2.5⇒n≥5

n=5 给 18.0 ms（恰好打平），n=4 给 18.625 ms 仍亏。关于这个 n：它是流水分块数，与 Store 对象数、传输切片数都不是一回事——一个流水块可以聚合多个对象，也可能被传输层再切成多个片；把搬运切细不会改变 key 的数量。此外公式还忽略了两类成本：每块固定开销 nα（α 够大时根本打不平，且最优块数要在整数范围内比较），以及同资源同方向的争用（公式的前提是两段不争用，若实际共享同一方向的容量，max 形式会向串行方向退化，退化多少取决于争用份额）。

(d) 推广到 TP8 需要补充：组时间取最慢 rank 加对齐时间，用平均值会系统性低估；“每 rank 20 GiB/s 网络、25 GiB/s H2D”必须对应一个按有向预算核过的真实拓扑（聚合 200 GiB/s 的 H2D 需求是否成立要看平台）；各 rank 必须对同一段连续前缀都成功，可跳过范围按最弱的 rank 折叠；对齐所需的同步由哪种机制实现、开销多大取决于框架，不能预设某种固定的集合通信；隔离实验排除掉的队列、元数据、布局转换与剩余计算要另计。

不能用命中率选方案：命中率只回答“有多少 token 可以不重算”，不回答“把这些字节搬过来是否比算更快”。本题 (a) 就是反例——命中 100%，理想界仍然亏。

题 3

(a) 六段之和 13+0.4+27+3700+45+1200=4985.4 ms。最大项是“IO 完成 → host 发布”的 3,700 ms（约 74.2%），次大项是“H2D 完成 → 入批”的 1,200 ms（约 24.1%）。

不能断定网络带宽不足：字节真正在链路上移动只有 27 ms，约占 0.54%；IO 排队 0.4 ms 说明提交后几乎立刻开始搬。若只把这 27 ms 压到零并保持其他区间长度不变，静态算术上的总时长只降 27 ms。真实改动还可能改变就绪时刻与后续准入机会，因此这不是系统改善的无条件上界；现有记录只表明两个最大区间发生在字节到达本机之后。

要算 IO 搬运段的稳态服务率，必须知道这一段实际搬运了多少字节（以及这些字节是否就是这一段全部的传输量）。本题没有给 payload，也不允许从题 1、题 2 借用——那两题的 0.3125 GiB 属于另一个场景的参数。所以这一段只能说“用了 27 ms”，不能折算成任何带宽数值，更不能据此判断链路快慢。

(b) 改动直接针对“发布确认”这个时间戳。若前三段保持不变，且发布确实提前了 Δ，则“IO 完成 → host 发布”这一段缩短 Δ。六段首尾相接，这个终点也是下一段的起点；后续时间戳可能跟着移动，各段时长要分别判断。检查点频率与执行开销尚未知，所以主动扫描本身不保证提前多少，也不能直接保证所有请求都会提前。

“总完成时间不变”的情形：设发布提前 Δ=3000 ms，设备拷贝本身仍需 45 ms 且资源空闲，于是 H2D 完成也提前 3,000 ms；但这个请求真正入批的时刻被每轮 token 预算卡在原处不变。那么“IO 完成 → 发布”变成 700 ms，“发布 → H2D 完成”仍是 45 ms，“H2D 完成 → 入批”从 1,200 ms 变成 4,200 ms，六段之和仍是 4,985.4 ms——等待只是从一段挪到了另一段。

仅凭现有信息无法确定变化幅度与因果：题目没有给 Δ、没有给队列深度与每轮预算的时间序列、也没有给其他请求的情况。如果这个请求原先正是因为“尚未确认”而错过了某一轮准入，那么提前确认可能让它赶上更早的一批，改善多少取决于后续的准入机会；而且其他请求的排队状态也会因此变化，反过来影响这一个。所以“准入规则没改”不能推出“某段时长不变”，单看总时长变没变也不能认定原因。

(c) 可接受的证据与它们各自排除的解释（任选四项以上）：

  • 这一段实际搬运的字节数与覆盖范围：用来把 27 ms 折算成服务率，判断它是接近字节下界还是以固定开销为主；没有这个量，(a) 里的带宽判断根本无法展开。
  • 对象数与粒度布局，以及 lookup/IO 是否批量提交：用来判断 13 ms 的 lookup 是一次往返还是很多次累加，以及控制面是否接近能力上限（对应第 3 节的对象率）。
  • 每次操作的返回结果与覆盖范围：用来区分“整段成功一次搬完”“分成多次且其中一些被重做”这两种完全不同的时间构成。
  • 等待队列深度与每轮 token 预算的时间序列：用来判断 3,700 ms 是否因为扫描迟迟到不了这个请求，以及 1,200 ms 是否由准入约束解释；这也是 (b) 里两种情形的区分依据。
  • 六段各自的起止时间戳；若实际采用 TP，再记录各 rank 的分布：用来判断是单个 rank 拖慢还是全组同时变慢，以及等待是否只是在相邻段之间转移。本题没有预设并行规模。
  • 同一资源同一方向上的争用情况：用来判断“发布 → H2D 完成”的 45 ms 是否因为同方向上还有其他流量在占容量；按第 4.2 节，要核的是真正共享的那段容量，而不是“挂在同一个节点下面”。

(d) 仍可复算或模拟的：给定前缀长度与模型形状时的字节预算与各层粒度换算；给定对象数与每对象处理成本时的控制面能力上限；给定字节数与服务率时的传输时间下界（本题缺字节，所以这一条要先补数据）；在给定到达过程、服务时间分布与准入策略下模拟排队与等待分布。必须标为未验证的：真实平台上的稳态服务率与每块固定开销；设备事件与流完成的实际时序；确认路径改动后的真实效果；以及“这组数字在某个具体系统上会按同样比例出现”这类推广——本题数据是为教学构造的，不是实测记录。

可测的未知参数

本页多处把一个量留成待测，因为它决定结论方向而不能靠推导得到：

  • 每块固定开销 α 与它和字节搬运的重叠程度。测法是固定字节与服务率、只扫块数，看总时间随块数的走势；第 4.2 节的相加形式只在“完全不重叠”时成立，重叠程度本身就是要测的东西。
  • 各段的稳态字节服务率，以及同资源同方向争用下的退化。要分别在隔离和并发两种条件下测，并按第 4.2 节的有向预算记录是谁和谁共享容量。
  • 控制面的每对象成本在不同批量方式与并发下的变化。20 μs 是教学值；真实值决定第 3 节的粒度结论是否仍然成立。
  • 解码成本 d 与 c（按产出可消费张量计），以及 GPU 解码对同卡计算的挤占。它们直接决定第 6.2 节的盈亏方向。质量侧需要在目标模型与任务上重测，不能沿用他人配置的结论。
  • 确认提前之后，等待在相邻区间之间如何重新分布。要同时记录各区间的起止时间戳、队列深度与每轮预算，并观察其他请求的排队变化；只看总时长无法归因。
