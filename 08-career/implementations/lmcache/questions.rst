推理 Infra / KV 存储面试：60 问与参考回答
=========================================

下面覆盖这类岗位常见的考察主题，不是某家公司的真实题库或频率统计。
回答先给结论，再给机制、边界和验证方法；涉及实现时以本指南的源码基线为准。
“正确回答”不意味着只有一种架构选择，而是推理自洽、假设明确、不会牺牲正确性。

基础与容量（Q1–Q12）
--------------------

Q1：为什么需要 KV Cache，为什么不缓存历史 Q？
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

普通自回归 attention 的新 query 会读取历史 K/V，所以缓存它们可避免重算历史前向。
历史 Q 通常不再用于后续 token 的 attention，缓存它不能获得相同收益。
KV 仍需从 HBM 读取，因此缓存不是消除 attention 计算或历史访存。
追问时写出 attention 方程，而不是只回答“加速推理”。

Q2：Prefill 与 Decode 的瓶颈有什么不同？
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Prefill 并行处理许多输入位置，常有较高计算强度；Decode 每步的新 token 少，
常受权重/KV 带宽与 batch 效率影响。长上下文 attention、MoE、量化和不同 batch
会改变瓶颈，所以应看 profiler 与 roofline，而不是绝对声称前者只算力、后者只带宽。

Q3：如何计算 KV Cache 大小？
~~~~~~~~~~~~~~~~~~~~~~~~~~~~

普通同构 attention 用 ``2 × layers × tokens × KV_heads × head_dim × dtype_bytes``。
例如 32 层、8 KV heads、128 维、BF16：128 KiB/token，8K 是 1 GiB。
这不包含 allocator 对齐、scale、buffer、副本和元数据；多序列按实际有效长度求和。
回答时同时注明 GB 与 GiB。

Q4：GQA/MQA 为什么能节省 KV？
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

多个 query heads 共用较少的 K/V heads，缓存按 KV heads 而非 query heads 计量。
MQA 通常只有一个 KV head，GQA 介于 MHA 与 MQA 之间。
这是模型结构设计，不是存储层把几个不同 head 的 KV 随意合并。

Q5：TP=8 时每张卡的 KV 一定是总量的八分之一吗？
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

只有 KV 头/状态均匀分片且没有复制时才成立。KV heads 少于 TP、MLA 的 latent
表示或某些引擎布局可能复制 KV；PP 又改变每 rank 持有的层。
应从实际 tensor/group layout 和 rank 语义求和，不能只看 TP 参数。

Q6：MLA 和滑窗模型怎么估算？
~~~~~~~~~~~~~~~~~~~~~~~~~~~~

MLA 应按引擎实际保存的压缩 latent、位置分量等计算；
滑窗层按实际窗口存储策略计算，full-attention 层仍可能线性增长。
混合模型还可能有递归状态快照，按 group 分别计量。
MLA 是 Multi-head Latent Attention，不应称作普通的多层 attention。

Q7：PagedAttention 解决了什么，不解决什么？
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

它通过逻辑块到物理页的映射减少为每条序列预留连续最大空间的浪费，
支持灵活分配和共享。但不自动提供跨进程远端存储，不让 KV 总量消失，
也不保证每个块都无内部碎片。分页管理、前缀复用和外部 offload 是不同能力。

Q8：APC 与 LMCache 有什么关系？
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

APC 复用引擎内已有 GPU 前缀块；LMCache 可扩展到主机内存、外部后端和独立服务。
两者可协作，但 GPU 已全命中的请求未必从 LMCache 读取。
实验须分别统计本地和外部命中，可用新引擎连接仍存活 server 的方式验证外部复用。

Q9：相同文本一定有相同 KV 吗？
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

不一定。模型权重、tokenizer、模板、前文、位置/RoPE、mask、LoRA 和多模态输入
都可能改变 KV。token IDs 相同也不足以绕过模型/位置和 layout 检查。
需要计算语义等价及物理解释兼容；“字符串相等”不是充分条件。

Q10：为什么 key 要包含前缀链？
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

同一文本块处在不同历史后面时，其 hidden state 与深层 KV 会不同。
把前一块 hash 纳入当前 hash，可以让历史变化传播到后续身份。
还需稳定编码、模型/租户 namespace 等；hash 抗碰撞不能替代正确的输入定义。

Q11：temperature 会让 prompt KV 失效吗？
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

通常不会，采样参数作用于 logits 之后，固定 prompt 的前向 KV 不变。
但采样导致的生成 token 不同会使后续上下文和 KV 不同。
如果其他配置实际改变了前向计算，要按具体实现判断，而不是把所有请求参数都盲目哈希。

Q12：命中整个 prompt 是否完全不需要模型计算？
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

不能笼统保证。某些引擎仍需重算末位 token 获得首个输出所需 logits，
并且存在完整 chunk、block 与调度接口的限制。
prefill 被大幅减少不等于 decode 消失，仍需为输出 token 执行模型。

LMCache 架构与正确性（Q13–Q25）
-------------------------------

Q13：用一分钟介绍 LMCache。
~~~~~~~~~~~~~~~~~~~~~~~~~~~

它是推理引擎与多级 KV 存储之间的管理/集成层，让本来短暂的 KV 可被后续请求复用。
Connector 连接调度与 GPU KV，存储管理器负责对象和层级，
adapter 对接文件、对象存储、Mooncake 等后端。
本基线推荐独立 MP 服务；它不是另一个完整的模型执行引擎。

Q14：MP 模式相对进程内模式的取舍是什么？
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

独立服务允许跨引擎共享与独立生命周期，隔离缓存服务的 CPU 工作和故障边界。
代价是 RPC、设备 IPC/共享内存、服务部署和更复杂的异步生命周期。
不是完全消除引擎侧开销，也不是只要 server 活着缓存就永不丢失。

Q15：Scheduler 与 Worker 各做什么？
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Scheduler 决定可跳过多少计算、何时分配 block 与调度请求；
Worker 处理实际 GPU buffer 的加载/存储及数据就绪依赖。
Connector 把两侧元数据连接起来。查询到 key 不等于数据已落在 worker 的目标 page。

Q16：lookup、prefetch、retrieve 有何不同？
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

lookup 判断候选对象并可触发预取；prefetch 把 L2 对象加载到可供消费的 L1，
并管理锁和 staging；retrieve 将已有可用对象搬进引擎 GPU KV。
LOOKUP ack、预取结果就绪、GPU 可读是三个独立时刻。

Q17：为什么先等 LOOKUP ack 再查询预取状态？
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

请求处理池可能重排两条 RPC；查询先到会看到尚未登记的任务，导致错误 miss。
只需等目标 server 自己的 ack，不必为所有 server 设置无关的全局 barrier。
当前 LookupState 用 callback 推进，同时限制 pending 时重查频率。

Q18：``None`` 与零命中为什么不能混用？
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

在相关异步查询接口中，``None`` 表示 pending，0 或空 bitmap 表示完成且没有命中。
把 pending 当 miss 会过早重算，把 miss 当 pending 会一直等待。
还应读清结果是否只消费一次，不能假设任意重复 query 幂等。

Q19：ObjectKey 编码了哪些东西？还缺什么？
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

本基线有 chunk_hash、model_name、kv_rank、object_group_id 和 cache_salt。
它们区分内容、模型命名、分片、group 与隔离域。
字段本身不保证模型 revision、LoRA、dtype 等全部被正确覆盖，
还要检查调用方 namespace、hash 输入和 layout 协商。

Q20：block 与 chunk 为什么不能混为一谈？
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

block 是引擎 GPU 分配/调度单位，chunk 是缓存分块与对象管理单位。
一个 chunk 可涵盖多个 block，也可能拆成多个 group/rank 对象。
尺寸要满足兼容与对齐；本基线 MP 可协商最终 chunk size，不应只相信启动请求值。

Q21：为什么要有 staging，而不是分配地址后立即可读？
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

地址可用不代表内容已完成。staging 把在写数据与已发布 resident 分开，
只有 fill/copy 完成后才 admission，避免读半成品。
不同 writer tag 可并发准备同 key，第一个发布者胜出，后来 staging 可安全丢弃。

Q22：缓存是不可变对象，为什么还需要锁？
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

不可变只解决内容修改，不解决对象在读取期间被淘汰、内存回收或地址复用。
读保留/租约保持数据生命周期；写保留保护发布前状态。
锁和引用应覆盖真正的数据操作，不只是 Python 调用或 RPC 提交。

Q23：GPU 异步传输最危险的 bug 是什么？
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

传输还没结束就释放/复用 source 或 destination，或消费流没等生产者事件。
表现可能是偶发错误答案而非崩溃。正确链路是计算完成→传输等待→copy 完成→
发布/消费→释放，不能把 future done 无条件当作 DMA 完成。

Q24：两个 TP rank 命中长度不同怎么办？
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

必须满足实际 forward 所需所有分片的共同有效范围。
普通前缀场景通常取共同最短前缀，并释放不会使用的尾部保留。
混合 group、滑窗和复制 KV 需要按其契约处理，不能把单 rank 最长结果广播给所有人。

Q25：抢占恢复为什么会产生缓存正确性问题？
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

GPU page 可能在旧 store 完成前被新请求复用，导致旧 key 存入新请求内容；
恢复时 computed-token 游标也可能与实际加载范围不一致。
需要对 page 复用、传输完成、进度重置和重新加载建立明确顺序，并测试高并发抢占路径。

存储、Mooncake 与 RDMA（Q26–Q40）
---------------------------------

Q26：LMCache 与 Mooncake 谁替代谁？
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

常见部署是组合关系。LMCache 连接推理语义、KV 生命周期和多级后端；
Mooncake Store 提供分布式对象池，Transfer Engine 提供数据传输。
也有不用 LMCache 的 Mooncake 集成，所以不能说两者必然绑定或完全等价。

Q27：Store 与 Transfer Engine 的区别？
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

Store 按 key 处理对象、分配、副本、租约与淘汰；Transfer Engine 按 segment
和注册地址搬运 bytes。直接 P/D 交接可以使用传输层而不建立长期 Store 对象。
只有传输能力并不自动产生跨请求前缀复用。

Q28：Mooncake Master 是否是数据带宽瓶颈？
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

它通常处理对象元数据、位置和生命周期，不中转大 payload，
Client 使用 Transfer Engine 直接访问数据。Master 仍可能成为控制面 QPS、
目录容量或可用性瓶颈，但不能用所有对象字节数除以 Master 网卡来估算其压力。

Q29：PutStart/PutEnd 的意义是什么？
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

先申请位置，再由 Client 写数据，最后把完成状态发布给后续读者。
分离分配与可读发布，避免读半写对象。失败路径必须回收未完成分配或保持不可读，
不能因为 PutStart 成功就认为对象已经完整存在。

Q30：读租约、TTL、soft pin 有什么区别？
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

读租约保护在途读取的有效期；TTL 可能指对象存活或其他过期策略，必须看具体接口；
soft pin 是更不易淘汰的提示/策略，并非永久持久化。
本基线 Mooncake soft-pin 生命周期不被普通读不断续期，读租约有独立语义。

Q31：多副本是不是强持久化？
~~~~~~~~~~~~~~~~~~~~~~~~~~~

不是。内存副本提高节点故障下的数据可用性，但集群断电仍可能丢失。
要说明写确认条件、副本独立故障域、持久介质以及恢复协议。
缓存可选择丢失后重算，但必须预算重算的 GPU 与 SLO 成本。

Q32：RDMA 为什么比普通 socket 可能更快？
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

它可减少内核协议栈与 CPU payload 拷贝开销，让 NIC 对已注册内存做 DMA，
并支持高效批量和单边操作。但仍有连接、元数据、提交、完成处理和注册成本，
小对象、差拓扑或低并发下不保证优于优化过的 TCP。

Q33：“零拷贝”究竟指什么？
~~~~~~~~~~~~~~~~~~~~~~~~~

是省去特定路径的中间 buffer/CPU memcpy，不是数据不经总线移动。
必须画出源、目标、NIC/GPU 和 staging，指出省掉哪次 copy。
LMCache 主机 L1 接 Mooncake RDMA 时仍可能有 GPU↔host 的拷贝。

Q34：为什么内存注册应复用？
~~~~~~~~~~~~~~~~~~~~~~~~~~~

MR 注册可能涉及 pin 页、地址映射、NIC 状态和系统调用，
逐对象频繁注册会限制小对象吞吐。注册 slab/内存池可摊销代价，
但需要控制总 pin 内存、碎片、权限与在途引用，不能无限注册。

Q35：CQ 完成和对象可读是同一回事吗？
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

传输完成是底层操作状态，对象可读还需要上层发布完整性、版本及位置元数据。
多片对象尤其不能在第一片完成时就作为整体发布。
反过来，软件发布如果先于设备完成，也会把未完成数据暴露给读者。

Q36：GPUDirect RDMA、GDS、NVLink 有什么区别？
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

GPUDirect RDMA 面向 NIC 与 GPU memory 的直接访问；GDS 面向存储↔GPU 数据路径；
NVLink 是 GPU 等设备之间的互连技术。它们的软硬件条件、拓扑和场景不同，
不能因为系统拥有其中一个就宣布具备另两个。

Q37：多网卡为什么不一定线性提速？
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

还可能受 PCIe root complex、NUMA、单流并发、远端 DRAM、CPU 提交速率或对象大小限制。
需要合理 striping 和足够在途工作，并测每个 NIC 的流量。
“两张 200G 卡”只是物理上界，不是应用稳定达到 50 GB/s 的证明。

Q38：LMCache 的 Mooncake adapter 有哪些接入陷阱？
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

MP native adapter 与旧进程内配置不同；要构建相应 C++ 扩展并匹配头文件/库。
RDMA 需要有效 L1 descriptor 和内存注册条件；非 LMCache 字段会转交 Mooncake，
不能期待自动修正错误服务地址。还要避免 LMCache HTTP 与 metadata 的端口冲突。

Q39：SGLang HiCache 的 L2 等于 LMCache L2 吗？
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

不等于。HiCache 常把 GPU、host、外部存储叫 L1/L2/L3；
LMCache MP 常把 host 管理层叫 L1、外部 adapter 叫 L2。
对比时先说物理介质和管理职责，不能只比较层号。

Q40：S3、Redis、远端内存谁最适合 KV？
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

取决于对象大小、复用间隔、容量成本、延迟预算、请求费用和运维能力。
大 KV 的延迟敏感复用通常更关注带宽与低拷贝路径；
冷缓存可用对象存储扩容；传统服务也可能适合中小规模或已有基础设施。
没有脱离 workload 的唯一正确选型。

性能与高级主题（Q41–Q50）
-------------------------

Q41：命中率高但 TTFT 更差，怎么排查？
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

拆 lookup、L2、网络、H2D、剩余 prefill 和队列，确认 hit 的长度与实际来源。
可能命中很短但固定查询开销大、远端读慢、数据转换重、或路由去更拥塞的实例。
用相同输入和并发对比读取与重算，不以命中率作为最终性能指标。

Q42：怎样判断读取还是重算？
~~~~~~~~~~~~~~~~~~~~~~~~~~~

比较省下的计算与查询、暴露传输、解码和干扰成本。
例如 1 GiB 走 200 Gbit/s 的网络理论下界约 43 ms，还要加其他阶段。
若只能省 20 ms prefill，通常不划算；有 overlap 时按关键路径而非简单相加判断。

Q43：chunk 应越大越好吗？
~~~~~~~~~~~~~~~~~~~~~~~~~

大 chunk 减少对象/提交开销，但增加过取、尾部浪费和部分命中损失；
小 chunk 相反，还可能令元数据/IOPS 变成瓶颈。
应满足引擎对齐条件，在固定 workload 下扫描大小并记录协商后的真实值。

Q44：为什么异步不一定提高吞吐？
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

异步只改变等待组织，不创造带宽；无限在途会耗尽 staging、增加排队和尾延迟。
有效异步需要可重叠的资源、完成通知、背压与取消机制。
用在途 bytes 而不只任务数限流，更适合长度差异大的 KV 请求。

Q45：LRU 有什么不足，如何改进？
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

它只近似利用最近性，不直接考虑对象大小、重算价值、前缀依赖与租户公平。
可考虑频率、成本/字节、前缀保护与准入过滤，但增加状态和预测误差。
先用访问 trace 验证比 LRU 更好，再引入复杂策略；不要把启发式说成理论最优。

Q46：缓存感知路由为何不能只选最长命中？
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

最长命中的节点可能队列最深或跨网传输最贵，整体完成时间反而更高。
结合 queue、可省计算、load、网络和公平性估算候选成本；
目录可能陈旧，实际加载还要验证。路由索引不是数据正确性的唯一来源。

Q47：CacheBlend 是否无损复用任意片段？
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

不是无条件保证。片段在新上下文中的深层 KV 会变化，
CacheBlend 用选择性重算处理依赖/质量恢复。
需要在目标模型与任务上验证质量和性能，不能用“文本重复”证明逐位等价。

Q48：压缩 KV 何时划算？
~~~~~~~~~~~~~~~~~~~~~~~

当减少的传输/存储成本大于编码、解码、scale 与质量代价时。
分别测压缩率、编码吞吐、解码关键路径、输出质量和端到端 SLO。
无损压缩、低精度量化与选择性丢 token 的正确性边界不同，不应混称同一方法。

Q49：P/D 分离和共享缓存分别解决什么？
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

P/D 分离把 prefill 与 decode 的计算和资源池拆开，通常需要本次请求的 KV 交接；
共享缓存让后续请求复用已计算状态。两者可组合，但任一个都不自动提供另一个。
当前 MP recipe 用 NIXL 做交接、LMCache 做跨请求复用，具体配置需核对版本。

Q50：怎么证明缓存没有破坏结果？
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

用固定模型/输入/dtype 的无缓存参考，验证冷写、热读、partial hit、并发、
跨 rank、取消和抢占。随机性及 batch 数值变化需先用无缓存对照校准。
精确复用看 token/logit 一致性及合理数值容差；有损策略还要任务质量指标。
仅 HTTP 200、形状正确或 CRC 正确都不充分。

系统设计与故障分析（Q51–Q60）
-----------------------------

Q51：设计 KV Cache 服务前先问什么？
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

模型/布局、上下文与输出长度分布、QPS/并发、共享前缀比例和复用间隔，
TTFT/ITL SLO、GPU/网络/存储条件、租户隔离、容错和预算。
然后分别算容量、读写带宽、对象/元数据数、在途空间和故障余量。
不要先画十个组件再猜负载。

Q52：存储掉一台机器，缓存可重算所以不用管吗？
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

仍要控制重算风暴：限流/背压、选择副本、降级慢层、保护 GPU，
并控制重新复制和预热流量。可重算意味着允许丢状态，不意味着 SLO 免费恢复。
必须按同时失效的热点容量与并发请求估算回源负载。

Q53：怎样避免并发重复加载同一个大对象？
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

可以设计 single-flight/合并等待者，或允许多个 staging、发布时去重，
各有锁复杂度和重复 I/O 的取舍。不能在持全局锁时做慢 I/O。
本基线 L1 的不同 writer tag 可 staging 同 key，并在 admission 决出 resident；
这不等于所有上层都已经合并了重复网络读取。

Q54：请求取消时可以立即释放 buffer 吗？
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

只有确认没有在途设备/网络操作会访问它才可以。
应停止新任务、标记状态、取消可取消的工作，等待或隔离不可取消 DMA，
然后释放锁、引用与地址映射。超时和 Python 对象析构不能自动证明硬件访问已停止。

Q55：如何处理热门 system prompt？
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

优先保证兼容的多实例复用，可增加副本、局部预热或固定一部分容量，
并结合负载均衡避免所有请求集中到一个“命中最长”的节点。
共享边界需要授权；不同模型版本、LoRA 或租户策略不允许盲目合并。
热点保护也需上限，避免 pin 满全部容量。

Q56：cache_salt 能替代认证吗？
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

不能。它提供 key 命名隔离，身份认证和授权决定谁有权使用哪个隔离域。
还需配额、网络与管理 API 控制，以及避免日志/指标泄露内容。
KV 本身也应按敏感状态管理，不能因为不是原文就认定无隐私风险。

Q57：为什么冷/热基准常常失真？
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

GPU APC、LMCache L1、OS page cache、远端 cache 和 kernel 预热可能不同步。
重复同一 prompt 可能只测到 APC；重启引擎首请求又混入初始化。
为每一级记录热状态，使用可复现 trace、独立数据目录和充分样本，并保留原始结果。

Q58：怎样设计一个新的 L2 adapter？
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

先读公开接口，明确 submit/完成通知/结果消费、锁、失败 bitmap 与 buffer 所有权；
再实现最小 store/lookup/load/unlock，加入超时、取消、部分失败与 shutdown 测试。
不能只实现同步 put/get 并阻塞 controller 主循环，也不能忽略 unlock 的最终完成契约。

Q59：面试官让你讲一个 KV Cache 优化项目，怎么组织？
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

按“业务负载与 SLO→基线瓶颈→假设→单变量实验→结果与质量→代价与失败路径”回答。
明确自己的贡献、环境与样本数量，给出可复现实验和关键 trace。
本指南的离线练习可以作为学习项目，但不能包装成自己运营过的生产集群。

Q60：被问到没读过的版本或实现细节怎么办？
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

说明已确认的原理与版本范围，然后列出要检查的接口、设计文档和测试。
例如“需要确认该 adapter 的 lookup 是原子锁还是租约模拟，并检查 load 失败路径”。
坦诚的不确定性与可执行验证方法，比捏造默认配置或宣称所有故障都自动恢复更可信。
